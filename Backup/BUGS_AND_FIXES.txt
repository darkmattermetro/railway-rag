1. clear_cache(delete_chunks=True) wipes ALL categories' caches
────────────────────────────────────────────────────────────────────────

  Files:    ingest.py:135-140, local_builder.py:77, build_index.py:119

  Before:
    def clear_cache(category, delete_chunks=False):
        if delete_chunks and _CACHE_DIR.exists():
            shutil.rmtree(_CACHE_DIR, ignore_errors=True)

    shutil.rmtree(_CACHE_DIR) removes .chunks_cache/ — a shared directory
    containing cached chunks for ALL categories.  Clicking "Start Fresh" on
    one category silently destroys cached data for every other category.
    Hours of docling conversion work lost in one click.

  After:
    Cache key format changes from {file_hash} to {category}__{file_hash}.
    clear_cache deletes only files matching its own category prefix.

    if delete_chunks and _CACHE_DIR.exists():
        prefix = f"{category}__"
        for p in _CACHE_DIR.iterdir():
            if p.name.startswith(prefix):
                (shutil.rmtree if p.is_dir() else p.unlink)(p)

  Change:  ~15 lines in ingest.py — _cache_key() helper, update 4 cache
           functions, update clear_cache.


2. No GPU→CPU fallback during embedding / FAISS build (4 GB VRAM)
────────────────────────────────────────────────────────────────────────

  File:     ingest.py:486-490

  Before:
    embeddings = HuggingFaceEmbeddings(
        model_kwargs={"device": "cuda"} if HAS_CUDA else {},
    )
    vector_store = FAISS.from_documents(batch, embeddings)

    After 45 minutes of processing on 4 GB VRAM, a moment of VRAM
    fragmentation causes torch.cuda.OutOfMemoryError.  Zero fallback,
    zero retry, zero batch-size reduction.  Entire build lost.

  After:
    try/except wrapping both embedding init AND each embedding batch.
    On CUDA OOM: halve batch size, fall back to CPU embeddings.

    except (RuntimeError, torch.cuda.OutOfMemoryError):
        logger.warning("CUDA OOM during embedding init, falling back to CPU")
        batch_size = max(batch_size // 2, 50)
        embeddings = HuggingFaceEmbeddings(
            model_name=..., model_kwargs={"device": "cpu"}, ...)

    Same protection around vector_store.from_documents / add_documents.

  Change:  ~20 lines in ingest.py.

10. Quota/error classifier over-broad + model exhaustion too aggressive
────────────────────────────────────────────────────────────────────────

  File:     model_selector.py:185-208, 274-285

  Before:
    _is_quota_or_rate_error uses substring matching on str(error).lower()
    — "exceeded", "limit exceeded", "429", "too many requests" — and
    catches broad Exception in the fallback loop.  A transient network
    timeout or a non-quota error containing any of these substrings gets
    classified as quota exhaustion, marking a key as exhausted for 10
    minutes.  With only 1-2 keys per provider, one false positive can
    rapidly exhaust all keys and break the app.

  After:
    1. Tighten _is_quota_or_rate_error to check exception TYPE first
       (ResourceExhausted, RateLimitError, APIStatusError with
       status_code 429/503), then substring as secondary heuristic.
    2. In the fallback loop, catch only known provider exceptions;
       let all other errors propagate with a traceback.

    def _is_quota_or_rate_error(self, error: Exception) -> bool:
        if isinstance(error, (ResourceExhausted, RateLimitError)):
            return True
        if isinstance(error, APIStatusError) and error.status_code in (429, 503):
            return True
        # substring heuristic only as last resort
        error_str = str(error).lower()
        return any(i in error_str for i in ['quota', 'rate_limit', 'ratelimit'])

  Change:  ~15 lines in model_selector.py.


11. Citation protocol inconsistency
────────────────────────────────────────────────────────

  File:     app.py:442-469

  Before:

        <used_chunks>[0, 2]</used_chunks>
    But the context string in the user prompt is just:
        "Context:\n{context_str}\n\nQuestion: ..."
    where context_str = "\n\n---\n\n".join(context_parts)

    The LLM sees chunk text but NO index labels.  It has to guess
    which index corresponds to which chunk based on content alone.
    Citations are unreliable — the LLM might reference index 2 when
    it actually meant the 4th chunk, or vice versa.

  After:

        context_str = "\n\n---\n\n".join(
            f"[{i}] {c}" for i, c in enumerate(context_parts)
        )

    This gives the LLM explicit mapping between numbers and chunks.
